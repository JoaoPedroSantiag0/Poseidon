# ADR-003: Modelo de Dados de CTI Baseado em STIX 2.1

**Status:** Proposed  
**Data:** 2026-09-20  
**Decisores:** Architect / Builder, Humano  
**Consultados:** Auditor  

---

## 1. Contexto e Declaração do Problema

Um dos erros mais comuns em plataformas de SOC é tratar Indicadores de Comprometimento (IOCs) como strings isoladas em tabelas simples (`value`, `is_malicious`). Essa abordagem desconsidera contexto, validade temporal, nível de confiança e relacionamentos entre ameaças.

A **Lei 2** define **STIX 2.1** como o padrão compulsório para objetos de Threat Intelligence.  
A **Lei 7** estabelece a proibição estrita de armazenar ou exibir "este IOC é malicioso" sem proveniência rastreável:
```
IOC → observação → { fonte, confiança, first_seen, last_seen, contagem, tags }
```

## 2. Decisão

Adotamos a especificação normativa **STIX 2.1 (OASIS Standard)** como a fundação de dados do CTI Engine do Poseidon.

### Detalhamento da Implementação:

1. **Entidades Relacionais no PostgreSQL (Core Metadata):**
   - `cti_indicators`: Mapeia SDO `indicator` STIX 2.1 (`id`, `pattern`, `pattern_type`, `valid_from`, `valid_until`, `confidence`, `name`, `indicator_types`).
   - `cti_threat_actors`: Mapeia SDO `threat-actor` (`name`, `aliases`, `threat_actor_types`, `sophistication`).
   - `cti_malware`: Mapeia SDO `malware` (`name`, `is_family`, `malware_types`, `capabilities`).
   - `cti_relationships`: Mapeia SRO `relationship` (`source_ref`, `target_ref`, `relationship_type`).
   - `cti_sightings`: Mapeia SRO `sighting` (`sighting_of_ref`, `where_sighted_refs`, `first_seen`, `last_seen`, `count`, `event_reference`).
2. **Proveniência Obrigatória (Garantia da Lei 7):**
   Nenhuma avaliação de reputação ou inteligência de ameaça existe sem origem explícita:
   - Toda ingestão (seja via OTX, VirusTotal, AbuseIPDB ou feed local) armazena:
     - `source`: Nome do provedor ou conector.
     - `confidence`: Nível numérico de certeza (0 a 100).
     - `observed_at`: Timestamps UTC precisos (`first_seen`, `last_seen`).
     - `raw_payload`: Resposta bruta da fonte externa preservada.
3. **Graph Rendering:**
   Os relacionamentos STIX 2.1 serão expostos via API para renderização de grafos investigativos no frontend com Cytoscape.js na Fase 10.

## 3. Alternativas Consideradas

### Alternativa A: Tabela Genérica Chave-Valor (`ioc_value`, `type`, `score`)
- **Vantagens:** Modelagem simples e rápida para MVP básico.
- **Desvantagens/Motivo da rejeição:** Violação expressa das Leis 2 e 7. Perda de rastreabilidade, impossibilidade de contextualizar campanhas e dificuldade extrema de migração futura para STIX.

### Alternativa B: STIX 2.1 Armazenado Cru como JSONB sem Schema Relacional
- **Vantagens:** Flexibilidade na ingestão direta de bundles JSON STIX.
- **Desvantagens/Motivo da rejeição:** Degradação de performance em queries relacionais de enriquecimento em tempo real e falta de validação estrita de integridade referencial.

### Alternativa C: Modelo Híbrido Relacional-STIX 2.1 (Escolhida)
- **Vantagens:** Tabelas relacionais indexadas para campos de busca rápida (hash, IP, domínio) combinadas com colunas JSONB para propriedades STIX avançadas e payloads brutos.

## 4. Consequências

### Positivas
- Total conformidade com a Constituição (Leis 2 e 7).
- Capacidade imediata de interoperar com feeds TAXII 2.1 e plataformas como MISP e OpenCTI.
- O analista visualiza exatamente *quem* afirmou a maliciosidade e com que nível de evidência.

### Negativas / Riscos / Dívidas Assumidas
- Requer normalização dos feeds externos (ex: converter respostas JSON do OTX em objetos STIX 2.1 válidos).

### Neutras / Impacto no Roadmap
- Fase 6 implementa o CTI Engine com conector OTX mapeando para STIX 2.1;
- Fase 10 utiliza o modelo STIX para alimentar o Entity Graph.
