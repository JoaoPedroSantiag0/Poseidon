# ADR-001: Papel do Wazuh e Implicações de Licenciamento dos seus Componentes

**Status:** Proposed  
**Data:** 2026-09-20  
**Decisores:** Architect / Builder, Humano  
**Consultados:** Auditor  

---

## 1. Contexto e Declaração do Problema

O Poseidon é uma plataforma modular de Security Operations Center (SOC) que se propõe a atuar como correlacionador agnóstico, camada de investigação contextualizada e plano de controle de resposta auditada. O Wazuh é uma ferramenta madura e amplamente disseminada de detecção baseada em host (HIDS), integridade de arquivos (FIM) e monitoramento de segurança.

A relação arquitetural entre o Poseidon e o Wazuh impõe desafios severos que, se mal equacionados, comprometem a identidade técnica e a viabilidade jurídica do projeto:

1. **Risco de Acoplamento e Identidade do Produto:** Conforme estabelecido na Seção 1 da Constituição: *"O Poseidon não é um frontend alternativo para o Wazuh. O Wazuh é um dos motores do Poseidon. Qualquer decisão de implementação que torne o Poseidon inseparável do Wazuh viola esta constituição."* O princípio operacional determina:
   ```
   O Wazuh detecta.
   O CTI contextualiza.
   O Poseidon Core correlaciona.
   O Investigation Workspace explica.
   O Analista decide.
   O Response Control Plane executa, sob autorização e registro.
   ```
2. **Riscos de Licenciamento Heterogêneo (Copyleft e Contaminação SaaS):** O ecossistema Wazuh divide-se em componentes autônomos com regimes de licenciamento distintos, auditados diretamente nos repositórios oficiais:
   - `wazuh/wazuh` (Manager, Analysis Engine, regras): Licenciado sob **GPLv2**.
   - `wazuh-indexer` (Core fork do OpenSearch): Licenciado sob **Apache-2.0**.
   - `wazuh-indexer-plugins` (extensões de autenticação e alertas): Licenciado sob **AGPL-3.0**.
   - `wazuh-dashboard` (plugin para OpenSearch Dashboards): Licenciado sob **GPLv2 e Apache-2.0**.
   - `wazuh-agent` v5.x (nova arquitetura do agente em desenvolvimento): Licenciado sob **AGPL-3.0**.
   Em um modelo de produto que visa distribuição e operação em modelo SaaS (decisão registrada em 2026-09-20), qualquer inclusão indevida de binários, modificação de código sob AGPL-3.0 ou empacotamento conjunto de bibliotecas pode impor obrigações desastrosas de abertura do código proprietário do Poseidon.
3. **Dualidade Estrutural de Conexão:** A API do Wazuh Manager (porta 55000) serve para gerenciamento de agentes, grupos, regras e execução de Active Response; ela **não serve alertas de detecção**. Os alertas são indexados no cluster do Wazuh Indexer (porta 9200) ou emitidos localmente no arquivo `alerts.json`. Portanto, qualquer conector com o Wazuh é duplo por necessidade arquitetural.
4. **Vulnerabilidades e Riscos do Wazuh Active Response:** Análise minuciosa do código-fonte do Wazuh (tag v4.14.7) revelou vetores críticos de abuso:
   - Comandos prefixados com `!` contornam a lista branca de comandos autorizados (`shared/ar.c`);
   - O parâmetro `agents_list` tem default `'*'`, disparando a ação em toda a frota caso omitido;
   - O endpoint `PUT /agents/upgrade_custom` permite instalar pacotes WPK arbitrários no endpoint;
   - Parâmetros de comandos podem ser interpolados sem escape adequado em endpoints legados.
   Conforme destacado no §2 (Lei 8) da Constituição: **a credencial da API do Wazuh equivale a execução remota de código em toda a frota.** Ela requer a mesma disciplina de proteção de uma chave criptográfica de assinatura.

## 2. Decisão

1. **Wazuh como Fonte Externa Secundária:** O Wazuh é classificado estritamente como um motor externo de detecção e fonte de telemetria. Ele não governa schemas, modelos de dados ou fluxos de decisão da plataforma.
2. **Conector Duplo e Isolado em Camada Adapter:** Toda a comunicação com o Wazuh será encapsulada no módulo `integrations/wazuh/`, expondo contratos de serviço genéricos (`DetectionEngineConnector`, `TelemetrySource`):
   - `WazuhManagerClient`: Interage via HTTPS com a REST API do Manager (porta 55000) com autenticação JWT para consultar inventário de agentes, status de saúde e políticas.
   - `WazuhIndexerClient`: Interage via REST API com o Wazuh Indexer (porta 9200) com credenciais segregadas (HTTP Basic/mTLS) para busca analítica de alertas nos índices `wazuh-alerts-4.x-*`, ou consome o fluxo de eventos via streaming de `alerts.json`.
3. **Proibição Absoluta de Fork do `wazuh-dashboard` (Lei 3):** Nenhum artefato, estilo ou componente do `wazuh-dashboard` será incorporado ao repositório do Poseidon. A interface do Poseidon é um SPA moderno independente (React 18, Vite, TypeScript, TailwindCSS, shadcn/ui).
4. **Segregação de Clusters OpenSearch:** O Poseidon operará seu próprio cluster OpenSearch 2.x upstream (licenciado sob Apache-2.0 puro) para indexação de telemetria normalizada e achados correlacionados, evitando acoplamento aos índices ou plugins sob AGPL-3.0 do `wazuh-indexer-plugins`.
5. **Autoimposição de Restrições no Active Response (Lei 8):** O Poseidon veda em nível de código qualquer abuso dos comportamentos permissivos do Wazuh Active Response. O conector `integrations/wazuh/`:
   - **NUNCA** envia comandos cujo nome inicie com o prefixo `'!'`;
   - **NUNCA** omite o campo `agents_list`, exigindo a especificação estrita do ID do agente alvo em cada despacho individual;
   - **NUNCA** invoca endpoints de atualização arbitrária como `PUT /agents/upgrade_custom`;
   - **NUNCA** deriva argumentos de execução a partir de entrada direta não-higienizada do usuário;
   - Opera exclusivamente através de conta de serviço no Wazuh Manager com perfil de privilégios mínimos (RBAC restrito);
   - Trata as credenciais da API do Wazuh como **chaves de execução de código**, armazenando-as com envelope encryption em repouso e auditando cada invocação no Audit Log (Lei 6).
6. **Papel no Ciclo de Validação da Lei 4:** O conector vivo do Wazuh será implementado na **Fase 9**, onde seus alertas atuarão como a segunda fonte heterogênea obrigatória para consolidar e congelar o modelo de dados OCSF introduzido na Fase 3.

## 3. Alternativas Consideradas

### Alternativa A: Forkar o `wazuh-dashboard` e customizá-lo como frontend do Poseidon
- **Descrição:** Desenvolver o Poseidon como um conjunto de plugins em cima do OpenSearch Dashboards customizado pelo time do Wazuh.
- **Vantagens:** Telas prontas de visualização de regras do Wazuh e inventário de agentes.
- **Desvantagens/Motivo da rejeição:** Violação frontal da **Lei 3**. O dashboard do Wazuh sofre regressões frequentes a cada versão upstream, acopla a evolução do produto ao roadmap de um fornecedor e submete a aplicação web a restrições de licenciamento GPLv2/AGPL.

### Alternativa B: Embutir binários e agentes do Wazuh diretamente no Collector Agent
- **Descrição:** Empacotar o `wazuh-agent` ou componentes C do OSSEC dentro do executável do Collector Agent do Poseidon.
- **Vantagens:** Reuso imediato de decoders locais e capacidade de FIM.
- **Desvantagens/Motivo da rejeição:** Violação da **Lei 8** (o agente deve ter superfície mínima, código Go estático e auditável) e contaminação integral do binário por copyleft estrito (**AGPL-3.0** do Wazuh Agent v5.x e **GPLv2** do Wazuh 4.x), inviabilizando distribuição comercial SaaS.

### Alternativa C: Integração Desacoplada via Conector Duplo e API REST Segregada (Escolhida)
- **Descrição:** O Poseidon consome o Wazuh estritamente por chamadas de rede via contratos bem definidos, tratando o Manager e o Indexer como serviços separados, e restringindo ativamente o Active Response.
- **Vantagens:** Neutralidade técnica absoluta, conformidade jurídica com as licenças Apache-2.0, GPLv2 e AGPL-3.0 (comunicação cliente-servidor por protocolo aberto de rede não gera obra derivada), resiliência a falhas de conectividade e blindagem contra comandos perigosos na frota.
- **Desvantagens:** Exige esforço de desenvolvimento do adaptador e normalizador de eventos na Fase 9.

## 4. Consequências

### Positivas
- Total conformidade com as Leis 1, 3, 4 e 8 da Constituição.
- Blindagem jurídica do modelo de negócio SaaS: nenhuma linha de código proprietário do Poseidon é contaminada por licenças GPLv2 ou AGPL-3.0.
- A frota monitorada pelo Wazuh ganha a camada de segurança do Poseidon, impedindo comandos massivos (`*`) e contornos de lista branca (`!`).
- Arquitetura verdadeiramente agnóstica: o Poseidon pode operar com ou sem Wazuh presente no ambiente.

### Negativas / Riscos / Dívidas Assumidas
- O conector precisa manter e sincronizar dois canais de comunicação com autenticações distintas (JWT no Manager e credenciais no Indexer).
- A latência de ingestão de alertas via polling/query no Indexer deve ser monitorada para garantir SLA de resposta em tempo hábil.

### Neutras / Impacto no Roadmap
- Fase 3 utiliza um corpus gravado de `alerts.json` reais do Wazuh (sem subir integração viva) para validar o modelo de dados provisório conforme a Lei 4;
- Fase 9 conclui a integração do conector duplo vivo do Wazuh e congela o modelo OCSF.

## 5. Conformidade Constitucional

- [x] Lei 1 — Fontes de licenciamento dos componentes e endpoints da API auditados com links oficiais e datas.
- [x] Lei 2 — Não inventamos schema: eventos recebidos do Wazuh são mapeados para OCSF 1.9.0.
- [x] Lei 3 — Não forkamos o `wazuh-dashboard`: frontend 100% autônomo.
- [x] Lei 4 — Wazuh entra na Fase 9 como segunda fonte real, impedindo que o modelo seja desenhado exclusivamente para o agente local.
- [x] Lei 5 — O tempo do evento (`timestamp` original do Wazuh) nunca é sobrescrito pelo tempo de ingestão do Poseidon; evento bruto é preservado.
- [x] Lei 6 — Ações disparadas via conector Wazuh são registradas no Audit Log append-only, separadas da narrativa de casos.
- [x] Lei 7 — Detecções do Wazuh que referenciam IOCs preservam a proveniência e confiança da fonte externa.
- [x] Lei 8 — O conector bloqueia comandos `!`, proíbe `*` em `agents_list`, veda `upgrade_custom` e trata credenciais como chaves de execução.
- [x] Lei 9 — Toda ação repassada ao Wazuh Active Response é objeto assinado, autorizado e auditado no Poseidon Control Plane.
- [x] Lei 10 — Failsafe de isolamento e regras de contenção são controladas prioritariamente pelo plano do Poseidon.
- [x] Lei 11 — Dados sensíveis contidos em alertas do Wazuh são submetidos a pipeline de redação.
- [x] Lei 12 — A saúde da conectividade com o Manager e o Indexer é monitorada continuamente pelo Health Center; perda de contato gera sinal.
- [x] Lei 13 — Atribuição e termos de uso de componentes e regras são respeitados na distribuição do produto.
