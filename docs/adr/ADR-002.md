# ADR-002: Modelo de Evento Normalizado: Adoção de OCSF 1.9.0 sobre ECS

**Status:** Proposed  
**Data:** 2026-09-20  
**Decisores:** Architect / Builder, Humano  
**Consultados:** Auditor  

---

## 1. Contexto e Declaração do Problema

O Poseidon processa telemetria heterogênea originada de fontes com naturezas radicalmente distintas: telemetria bruta de sistema operacional (ETW, Windows Security Log, Defender Antivírus local) coletada pelo Collector Agent próprio, e alertas interpretados emitidos por motores externos como o Wazuh ou futuros EDRs.

A interoperabilidade e a capacidade analítica da plataforma dependem da adoção de um schema normalizado aberto e consolidado na indústria:
- A **Lei 2 da Constituição** veda schemas proprietários ("Não inventamos schema"), fixando a escolha entre OCSF e ECS;
- A **Lei 4** estabelece a separação estrita entre **decidir o padrão** (Fase 3, nascendo como modelo `PROVISÓRIO`) e **congelar o modelo** (Fase 9, mediante ADR específico após validação contra no mínimo duas fontes heterogêneas). Para garantir que o normalizador não nasça viciado, a Fase 3 impõe o uso de **dois corpora gravados obrigatórios**: `alerts.json` real do Wazuh e telemetria bruta de endpoint (`.evtx`/`.etl` de máquina real);
- A **Lei 5** estabelece requisitos semânticos obrigatórios para todo evento, exigindo que o tempo do evento (`time`) nunca seja confundido com o tempo de ingestão, e que o dado bruto original seja preservado;
- A **Lei 13** impõe que metadados de atribuição (ex: autor de regras Sigma sob DRL 1.1) acompanhem o schema dos eventos e achados.

Uma auditoria prévia identificou que versões anteriores deste documento referenciavam schemas OCSF obsoletos (v1.1.0/v1.3.0), apontavam para classes depreciadas e mapeavam indevidamente o Registro do Windows para a classe de memória (1004). O presente ADR fundamenta-se inteiramente na consulta direta à API normativa do **OCSF versão 1.9.0** (`https://schema.ocsf.io/api/version`).

## 2. Decisão

Adotamos o **OCSF (Open Cybersecurity Schema Framework) versão 1.9.0** como o padrão canônico de normalização de eventos de telemetria, achados de segurança e ações de remediação no Poseidon.

### 2.1 Mapeamento Canônico de Classes (OCSF 1.9.0)

O OCSF 1.9.0 estrutura-se em 8 categorias formais. O Poseidon adota formalmente o seguinte mapeamento de classes para cobrir sua superfície de telemetria e resposta:

| Domínio do Evento | Categoria OCSF | Classe OCSF 1.9.0 | UID | Observações Normativas |
|---|---|---|---|---|
| **Criação / Encerramento de Processo** | Category 1 (System Activity) | `process_activity` | **1007** | Mapeia ETW `Kernel-Process` e Windows Security Event 4688. |
| **Conexões de Rede (TCP/UDP)** | Category 4 (Network Activity) | `network_activity` | **4001** | Mapeia ETW `Kernel-Network`. |
| **Resoluções DNS** | Category 4 (Network Activity) | `dns_activity` | **4003** | Mapeia ETW `Microsoft-Windows-DNS-Client`. |
| **Atividade em Arquivos** | Category 1 (System Activity) | `file_system_activity` | **1001** | Operações de criação, modificação e exclusão de arquivos. |
| **Registro do Windows (Chaves)** | Extensão `win` | `win/registry_key_activity` | **201001** | OCSF Core não possui classe de registro (1004 é `memory_activity`). A extensão oficial `win` é o padrão normativo. |
| **Registro do Windows (Valores)** | Extensão `win` | `win/registry_value_activity` | **201002** | Modificação e criação de valores no registro via extensão `win`. |
| **Autenticação e Logon** | Category 3 (Identity & Access) | `authentication` | **3002** | Eventos Windows 4624/4625. A antiga classe 3001 (`account_change`) foi depreciada na 1.9.0 em favor de 3006 (`user_management`). |
| **Alertas e Detecções de Segurança** | Category 2 (Findings) | `detection_finding` | **2004** | Alertas gerados por regras Sigma, detecções Wazuh e Defender AV. A antiga classe **2001 (`security_finding`) está depreciada desde o OCSF 1.1.0**. |
| **Ações de Remediação (Controle)** | Category 7 (Remediation) | `remediation_activity` | **7001** | Registro de ações de contenção e mitigação (`KILL_PROCESS`, `QUARANTINE_FILE`). |
| **Isolamento de Rede (Failsafe)** | Category 7 (Remediation) | `network_remediation_activity` | **7004** | Ações de isolamento e restauração de rede (`NETWORK_ISOLATE`, `NETWORK_RESTORE`). |

### 2.2 Conformidade Semântica com a Lei 5 nos Campos OCSF

Em cumprimento rigoroso à Lei 5, os seis conceitos semânticos são materializados estritamente nos atributos padronizados do OCSF 1.9.0, sem criação de campos inventados fora do padrão:

```json
{
  "class_uid": 1007,
  "category_uid": 1,
  "activity_id": 1,
  "time": 1790000000123,
  "metadata": {
    "version": "1.9.0",
    "product": {
      "name": "poseidon-collector-agent",
      "vendor_name": "Poseidon",
      "version": "0.1.0"
    },
    "profiles": ["host"],
    "uid": "evt-8f3b2a74-9876-5432-10ab-cdef01234567",
    "original_time": "2026-09-20T10:15:30.123456Z",
    "logged_time": 1790000002456,
    "modified_time": 1790000002456,
    "correlation_uid": "corr-uuid-9876-5432",
    "loggers": [
      {
        "name": "poseidon-ingestion-worker",
        "logged_time": 1790000002456
      }
    ]
  },
  "raw_data": "{\"Event\":{\"System\":{\"EventID\":4688,...}}}",
  "actor": {
    "user": { "name": "SYSTEM", "uid": "S-1-5-18" },
    "process": { "pid": 1024, "name": "services.exe" }
  },
  "process": {
    "pid": 4812,
    "name": "cmd.exe",
    "cmd_line": "cmd.exe /c whoami",
    "file": { "path": "C:\\Windows\\System32\\cmd.exe" }
  }
}
```

- **Tempo do evento:** Atributo raiz `time` (inteiro de milissegundos UTC desde o epoch);
- **Tempo de ingestão:** `metadata.logged_time` (quando o Poseidon registrou o evento) e `metadata.loggers` (rastreamento de hops pelo pipeline);
- **Origem:** `metadata.product` e `metadata.profiles`;
- **Identificador na origem:** `metadata.uid` e `metadata.original_time`;
- **Referência ao bruto e preservação:** `raw_data` contém o payload bruto original íntegro; artefatos maiores ou eventos em bloco apontam para o Object Storage via metadados de extensão;
- **Correlação:** `metadata.correlation_uid`.

### 2.3 Tooling e Implementação em Python
Para modelagem e validação em tempo de execução no backend Python 3.12, adotamos a biblioteca **`py-ocsf-models`** (mantida pela Prowler Cloud sob licença Apache-2.0, versão `v0.10.0+`), compatível nativamente com **Pydantic v2**, garantindo validação de tipos em alta performance sem necessidade de manter schemas manuais.

### 2.4 Ciclo de Vida: Modelo Provisório e Congelamento (Lei 4)
1. **Fase 3 (Decisão e Provisório):** O modelo OCSF 1.9.0 é adotado e implementado em código como `PROVISÓRIO`. Ele será obrigatoriamente exercitado e validado contra **dois corpora gravados heterogêneos**:
   - `corpus/wazuh_alerts.json`: Alertas reais emitidos por container Wazuh em execução de laboratório;
   - `corpus/endpoint_telemetry.json`: Telemetria bruta de ETW e Windows Security Log (Event 4688) capturados de uma máquina Windows real com script de extração descartável.
2. **Fases 4 a 8:** O pipeline de ingestão e o Collector Agent são desenvolvidos sobre esse modelo provisório, mantendo migrações e mapeamentos reversíveis.
3. **Fase 9 (Congelamento Formal):** Com o conector vivo do Wazuh implementado como segunda fonte real de telemetria e o Collector Agent operando na Fase 5, o modelo de evento será auditado contra ambas as fontes reais e formalmente congelado via **ADR específico** (`Supersedes: ADR-002`).

## 3. Alternativas Consideradas

### Alternativa A: Elastic Common Schema (ECS 9.5.0)
- **Descrição:** Adotar o ECS, atualmente em sua versão 9.5.0 mantido sob licença Apache-2.0 e migrado para colaboração com OpenTelemetry.
- **Vantagens:** Ampla documentação para logs de sistemas operacionais, histórico consolidado no ecossistema Elasticsearch/OpenSearch.
- **Desvantagens/Motivo da rejeição:** O ECS foca primariamente em campos planos de logs de infraestrutura e rede. O OCSF foi desenhado especificamente para segurança da informação e possui vantagens decisivas para o Poseidon:
  1. A Categoria 7 (`Remediation`), introduzida formalmente no OCSF, provê classes nativas (`7001` e `7004`) para modelar o Response Control Plane do Poseidon, algo inexistente no ECS;
  2. Especialização detalhada de achados em `detection_finding` (2004) e `vulnerability_finding` (2002);
  3. Governança multi-fornecedor sob a Linux Foundation (AWS, Splunk, IBM, CrowdStrike, Trellix), blindando o projeto contra diretrizes comerciais de um único player.

### Alternativa B: Modelo Proprietário Customizado ("Poseidon Internal Model")
- **Descrição:** Desenvolver um schema JSON próprio otimizado para o banco do Poseidon.
- **Vantagens:** Liberdade total de nomenclatura de campos.
- **Desvantagens/Motivo da rejeição:** Violação frontal da **Lei 2**. Isola o Poseidon, quebra a interoperabilidade com regras de detecção públicas (Sigma) e feeds de Threat Intelligence, e impõe custo de manutenção perene e proibitivo.

### Alternativa C: OCSF 1.9.0 (Escolhida)
- **Vantagens:** Padrão aberto consolidado, taxonomia nativa para telemetria de endpoint, detecção e ações de remediação, suporte a extensões formais (`win`) e validação via `py-ocsf-models` no Pydantic v2.

## 4. Consequências

### Positivas
- Total aderência às Leis 1, 2, 4, 5 e 13 da Constituição.
- O Response Control Plane (Fase 8) usará classes nativas do OCSF (`7001` e `7004`) para registrar ações de isolamento e contenção, unificando telemetria e resposta no mesmo vocabulário.
- A preservação integral do evento bruto em `raw_data` assegura valor forense incontestável.
- Validação rápida e estrita em Python através de Pydantic v2 e `py-ocsf-models`.

### Negativas / Riscos / Dívidas Assumidas
- O OCSF 1.9.0 possui centenas de atributos e validações estritas de enums (`activity_id`, `category_uid`, `type_uid`). Normalizadores exigirão testes unitários exaustivos na Fase 3.
- Eventos de Registro do Windows dependem da extensão formal `win` (`win/registry_key_activity`), exigindo configuração de namespace na biblioteca de validação.

### Neutras / Impacto no Roadmap
- Fase 3 cria os schemas provisórios e os valida contra os dois corpora gravados heterogêneos;
- Fase 5 integra o Collector Agent com ETW emitindo eventos mapeados para as classes 1007, 4001, 4003, 3002 e extensão `win`;
- Fase 9 congela o modelo formalmente com ADR próprio após validação viva do conector Wazuh.

## 5. Conformidade Constitucional

- [x] Lei 1 — Schemas, categorias e classes validadas diretamente nos endpoints da API oficial do OCSF 1.9.0 com citações e datas.
- [x] Lei 2 — Adoção integral do OCSF 1.9.0; campos estendidos sob namespace `poseidon.*`.
- [x] Lei 3 — Independência de schemas: não há dependência do modelo visual ou de índices do `wazuh-dashboard`.
- [x] Lei 4 — Decidir agora não congela o modelo: o modelo nasce `PROVISÓRIO` na Fase 3 sob dois corpora gravados e só é congelado na Fase 9.
- [x] Lei 5 — `time` do evento nunca é o tempo de ingestão (`metadata.logged_time`); evento original preservado em `raw_data`.
- [x] Lei 6 — Audit Log e Case Timeline mantêm schemas próprios segregados dos eventos de telemetria OCSF.
- [x] Lei 7 — Atributos de IOCs associados a eventos preservam a proveniência do enrichment.
- [x] Lei 8 — Ações de remediação representadas em classes OCSF 7001/7004 respeitam o catálogo fechado de capacidades.
- [x] Lei 9 — Eventos de resposta OCSF 7001/7004 refletem o ciclo de vida do objeto assinado da Lei 9.
- [x] Lei 10 — Ações de isolamento de rede modeladas em `network_remediation_activity` (7004) registram os metadados de failsafe e regras aplicadas.
- [x] Lei 11 — Linhas de comando mapeadas para `process.cmd_line` passam por sanitização prévia antes da serialização OCSF.
- [x] Lei 12 — Falhas de mapeamento ou campos ausentes (ex: ausência de linha de comando por falta de GPO) geram eventos de degradação de saúde no Health Center.
- [x] Lei 13 — Metadados de regras de detecção mapeados em `detection_finding` (2004) retêm identificação do autor e licença (DRL 1.1).
