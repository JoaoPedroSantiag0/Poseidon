# ADR-002: Modelo de Evento Normalizado: Adoção de OCSF sobre ECS

**Status:** Proposed  
**Data:** 2026-09-20  
**Decisores:** Architect / Builder, Humano  
**Consultados:** Auditor  

---

## 1. Contexto e Declaração do Problema

O Poseidon processa telemetria heterogênea originada de agentes locais (Sysmon, Security Log, Defender AV) e motores externos (Wazuh, EDRs futuros).

A **Lei 2 da Constituição** estabelece a obrigatoriedade de adotar um padrão aberto consolidado da indústria, indicando preferência por OCSF ou ECS, com definição formal em ADR-002. Adicionalmente:
- A **Lei 4** exige que o modelo normalizado só seja congelado após validação prática contra no mínimo duas fontes heterogêneas (Sysmon e Wazuh).
- A **Lei 5** exige que todo evento segregue categoricamente `event_time` de `ingestion_time`, preservando metadados de proveniência (`source`, `source_event_id`, `raw_reference`, `correlation_id`).

## 2. Decisão

Adotamos o **OCSF (Open Cybersecurity Schema Framework)** na versão `v1.3.0+` como o padrão canônico de normalização de eventos e achados de segurança no Poseidon.

### Detalhamento da Decisão:

1. **Classes Canônicas Mapeadas:**
   - `Class 1007 (Process Activity)`: Criação e término de processos (Sysmon Event 1, Windows Event 4688).
   - `Class 4001 (Network Activity)` e `Class 4003 (DNS Activity)`: Conexões e resoluções de nomes (Sysmon Events 3 e 22).
   - `Class 1001 (File System Activity)`: Operações em arquivos (Sysmon Event 11).
   - `Class 1004 (Registry Activity)`: Modificações no Registro do Windows (Sysmon Event 13).
   - `Class 3001 (Authentication)`: Eventos de logon/logoff e falhas (Windows Security 4624, 4625).
   - `Class 2001 (Security Finding)`: Normalização de alertas de detecção (Alertas Wazuh, Defender AV Events 1116/1117).
2. **Envelope Mandatório do Poseidon (Garantia da Lei 5):**
   Todo evento normalizado no Poseidon conterá, em seu nível raiz ou objeto de metadados, o envelope:
   ```json
   {
     "event_time": "2026-09-20T10:15:30.123456Z",
     "ingestion_time": "2026-09-20T10:15:32.456789Z",
     "source": "collector-agent",
     "source_event_id": "SYS-00048192",
     "raw_reference": "s3://poseidon-raw-events/2026/09/20/evt-uuid.json",
     "correlation_id": "corr-uuid-987",
     "ocsf_class_uid": 1007,
     "ocsf_data": { ... }
   }
   ```
3. **Extensões Específicas do Poseidon:**
   Qualquer atributo não contemplado pelo OCSF será isolado em objeto com namespace `poseidon.*` (ex: `poseidon.investigation_tags`, `poseidon.risk_modifier`).
4. **Condição de Congelamento (Lei 4):**
   O schema não será congelado na Fase 3. Ele será modelado inicialmente para o Collector Agent (Fase 5) e só será declarado estável após ser exercitado contra o Wazuh na Fase 9.

## 3. Alternativas Consideradas

### Alternativa A: Elastic Common Schema (ECS)
- **Vantagens:** Mapeamentos amplamente conhecidos para Windows Event Log e integração tradicional em pilhas Elasticsearch.
- **Desvantagens/Motivo da rejeição:** O ECS historicamente vinculou-se à governança da Elastic. Com a migração do ECS para o ecossistema OpenTelemetry e a adoção do OpenSearch pelo Poseidon, o OCSF surge como um padrão verdadeiramente multi-vendor (Linux Foundation, AWS, IBM, Splunk), projetado desde o princípio para interoperabilidade em Data Lakes de segurança sem favorecer um backend específico.

### Alternativa B: Modelo Proprietário Customizado ("Poseidon Event Schema")
- **Vantagens:** Controle total sobre cada chave e tipagem.
- **Desvantagens/Motivo da rejeição:** Violação frontal da Lei 2. Um modelo caseiro isola a plataforma, impede o reuso de regras Sigma comunitárias sem tradutores complexos e encarece a integração com novos motores de telemetria.

### Alternativa C: OCSF (Escolhida)
- **Vantagens:** Neutralidade de fornecedor, governança na Linux Foundation, separação clara entre atividades de sistema (`System Activity`) e detecções (`Security Finding`), com suporte a extensões padronizadas.

## 4. Consequências

### Positivas
- Interoperabilidade nativa com sistemas de Threat Intelligence, SIEMs e Data Lakes modernos (ex: Amazon Security Lake).
- Regras Sigma compiladas para OpenSearch mapeiam com fidelidade atributos padronizados de processo, rede e arquivo.
- O evento bruto original permanece preservado e acessível via `raw_reference`, mantendo integridade forense irrefutável.

### Negativas / Riscos / Dívidas Assumidas
- OCSF é um schema rico e profundo; mapeamentos exigem atenção a enums obrigatórios (ex: `activity_id`, `category_uid`, `class_uid`). Será desenvolvido validador em Pydantic na Fase 3.

### Neutras / Impacto no Roadmap
- Fase 3 implementa os modelos base OCSF (Classes 1007, 3001, 2001);
- Fase 5 exercita contra Sysmon e Security Log;
- Fase 9 conclui a validação contra o Wazuh e congela a versão `v1.0` do modelo.

## 5. Conformidade Constitucional

- [x] Lei 1 — Schema OCSF e classes verificadas em `schema.ocsf.io`.
- [x] Lei 2 — Não inventamos schema; adotamos padrão aberto com extensões isoladas em `poseidon.*`.
- [x] Lei 4 — Congelamento travado até validação contra fontes heterogêneas (Fase 9).
- [x] Lei 5 — `event_time` rigorosamente separado de `ingestion_time`; evento bruto preservado.
